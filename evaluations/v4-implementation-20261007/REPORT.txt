JOSHSPOT V4 SIMPLIFIED — LOCAL IMPLEMENTATION REPORT
7 October 2026

Status: Implemented locally for deterministic testing. Not approved for LIVE.
No deployment, production configuration change, production customer/database
write, calculator edit, or paid model evaluation was performed.

This directory contains new results. Prior V2/V3 evaluation artifacts were not
overwritten. File paths below are relative to the backend repository unless

1. V4 ARCHITECTURE

Actual inbound batch + bounded delivered history + small trusted state
  -> Responses API interpreter with strict Structured Outputs
  -> deterministic resolver using approved catalogue and existing calculator
  -> Answer Pack
  -> Responses API composer with strict Structured Outputs
  -> deterministic validation, at most one composer repair
  -> existing guarded draft/outbox/handoff infrastructure.

There is no model business-tool loop, model-selected database key, LLM judge,
or backend customer-sentence classifier. Ordinary interpretation belongs to the
first model. Business record lookup/calculation/action authorization belongs to
the backend. The second model writes from the Answer Pack.

Normal text turn: two model calls. Failed composition: at most three calls in
total. Interpreter/provider failure does not enter a tool-recovery loop.
Unsupported media/sensitive input can hand off before either model call.

Entry points: inbox/ai/v4/index.js, resolver.js, model.js, worker.js.
The existing pure V3 pricing adapter and read-only catalogue loader are reused;
the V3 conversational loop is not invoked.

2. EXACT INTERPRETER SCHEMA

See interpreter-schema.json, exported directly from inbox/ai/v4/schema.js.
All object fields are required; optional values are explicitly null; extra
properties are rejected. The backend independently checks the same shape.

Top-level fields:
current_requests[], facts[], purchase_change, readiness, whole_purchase_cap,
knowledge_needs[], clarification.

Request/fact/selection evidence is {messageId,text}; text must be an exact,
nonempty substring of a current inbound message. Old history cannot be used
as current authorization. This checks provenance, not the correctness of the
model's interpretation of that text.

5. RESOLVER ROUTING TABLE

ASK_PRICE / ACCOUNT_SETUP -> unique enabled service price; setup quote.
ASK_QUOTE / ADS_MANAGEMENT -> validated scoped inputs -> existing calculator.
ASK_RECOMMENDATION -> configured plans that pass calculator verification.
Package duration / ASK_BREAKDOWN -> plan lookup + calculator verification.
ASK_REQUIREMENTS -> service requirements + eligible approved knowledge.
ASK_SERVICE_INCLUSIONS -> eligible approved knowledge/service descriptions.
ASK_EXPECTED_RESULTS -> eligible expected-results knowledge.
ASK_CREATIVE_REQUIREMENTS -> eligible creative knowledge, otherwise unresolved.
ASK_TECHNICAL_HELP -> applicable approved technical knowledge.
ASK_COURSE_DETAILS -> course record/link + applicable knowledge.
ASK_PAYMENT_DETAILS -> quote/readiness/ownership/configuration guards -> invoice.
CLAIM_PAYMENT -> trusted payment status; never a model-created PAID state.
REQUEST_HUMAN -> existing assignment/handoff workflow before composition.
NEGOTIATE -> owner-approved non-negotiable policy; never lower the price.
OTHER -> available approved context and necessary clarification.

Explicit new budget/duration/package facts can also trigger recalculation.
Setup does not require campaign budget or duration. A multi-item all-inclusive
cap with one management item subtracts setup fees before using the existing
inverse calculator; several management items require allocation clarification.
The model does not invent an allocation.

6. KNOWLEDGE RETRIEVAL

inbox/ai/v4/knowledge.js uses semantic-topic and platform/service eligibility,
exclusions, priority, mandatory priority and lightweight query-word ranking.
At most three records per need and nine unique records per Answer Pack.
It does not embed or inject the entire catalogue.

The existing Knowledge Base editor now exposes an advanced V4 retrieval group:
v4Topics, v4Platforms, v4Services, v4ExcludedServices, v4Mandatory.
These are stored on the existing records, not in a duplicate knowledge system.
No production metadata was populated automatically.

A small explicit compatibility registry maps known existing record keys to
semantic topics. It maps business records, not customer phrases. Unknown old
records are not silently imported as behavioral authority. Legacy workflow
state updates, required questions and handoff flags do not drive V4.

The local saved snapshot contains 57 knowledge records; 12 have a compatibility
topic mapping. See local-knowledge-metadata.json for every record. Many of the
other records are old flow/template rules; approved factual records still need
owner-reviewed metadata. Mapping is not proof that a record will be retrieved:
scope, unresolved placeholders and financial-prose checks also apply.

Unresolved template placeholders and obvious currency-bearing knowledge prose
are excluded so service/plan/calculator records remain price authority. This
is conservative and can omit useful explanations. Missing or conflicting
knowledge must be reviewed before LIVE; this task did not modify production KB.

7. SMALL PURCHASE STATE

Namespaced at Conversation.ai.v4; no old engine state is deleted.
purchaseItems[] contains platform, service, confirmed status and current
evidence, plus scoped budget/duration/package facts when supplied.
Other fields: currentQuote, activeInvoice, verifiedPayment, readiness,
purchaseCap, unresolvedRequests, ownership and simulated-invoice retry metadata.

KEEP retains items; ADD merges exact pairs; REPLACE replaces selections;
REMOVE removes only named pairs. A different REPLACE clears the previous
whole-purchase cap. New facts and catalogue changes invalidate stale quotes.
Counteroffers never become accepted advertising budgets.

8. ANSWER PACK CONTRACT

The resolver constructs this internal object; it is not generated by a model:

{
  requests: current structured requests[],
  priorUnresolved: prior unresolved requests[],
  purchase: confirmed purchase items[],
  customerFacts: current evidenced facts[],
  facts: [{type: MONEY|FACT, role, value, source, field, platform, service}],
  knowledge: [{source, revision, topic, title, facts, explanation, scope,
               exclusions, mandatory}],
  plans: verified authoritative plan results[],
  quote: authoritative calculator quote | null,
  actions: {payment?: trusted status, invoice?: action result,
            handoff?: {accepted, pending?, simulation?, reason}},
  missing: question-field names[],
  allowedQuestions: question-field names[],
  readiness: readiness enum,
  verifiedPayment: trusted paid record | null,
  unresolvedRequests?: unresolved current requests[],
  resolutionError?: controlled backend failure/review code
}

The early human-handoff path deliberately avoids unnecessary knowledge/pricing
work. Composer receives the pack, not an independent raw-history instruction.

10. FINAL VALIDATION

inbox/ai/v4/validation.js checks response size, declared request coverage,
allowed question fields, internal-envelope leakage, approved URLs, canonical
payment instructions, account substitutions, unsupported monetary role/value
claims, false payment/invoice confirmations, result guarantees and discounts.
It accepts numeric and basic English number wording and allows ordinary
customer budget/duration/count references. Financial roles distinguish setup,
management, advertising spend, course and total.

Only one composer repair is permitted. A second invalid response fails closed
and the worker prepares/performs safe technical handoff according to mode.
The core does not issue another interpretation call to chase a passing reply.

Limits: declared coverage/questions are model metadata, not independent proof
of semantic coverage. Lightweight financial/guarantee checks cannot recognize
every possible English implication. Cross-platform contextual attachment of
otherwise approved numbers is not a complete semantic theorem. Real-model
review is required; these checks must not be described as perfect guarantees.

11. PAYMENT FLOW

Current ASK_PAYMENT_DETAILS + READY_TO_PAY + authoritative valid quote + no
missing action inputs + enabled invoices + valid ownership/configuration are
required. New DEFERRED/DECLINED state blocks invoice creation.
Paid/conflicting/expired invoices require review, not silent replacement.

TEST and DRAFT simulate invoice results and have no financial port invocation.
Simulation cache cannot substitute for a real LIVE action. LIVE requires the
explicit backend gate and saved mode/auto-reply settings. The V4 financial
adapter reuses the existing invoice generator with V4-prefixed idempotency and
quote fingerprint. Ownership is checked before sensitive writes/provider work.

Payment claims read/refresh trusted invoice status. They do not mark paid.
Composer receives exact persisted account/link text. Existing unpaid invoices
do not force those details into every unrelated answer.
If composition fails after a real invoice has been created, the invoice remains
idempotently recorded for staff review; the customer is not sent invented data.

12. HANDOFF FLOW

Current human request is resolved before optional business lookup. In LIVE the
worker invokes the existing durable assignment/notification workflow before
composition. V4 alone defers that workflow's acknowledgment until composition.
Composer sees whether assignment succeeded or is pending because no staff is
available. The acknowledgment uses the existing handoff outbox key and guard.
Other engine handoff behavior is unchanged.

The transferred conversation is rechecked for version, assignment, latest
inbound, configuration and engine before acknowledgment. A further human change
or engine switch cancels it. Pending assignment uses existing recovery.
TEST/DRAFT simulate the handoff; they do not assign real staff.
Unsupported media/sensitive input uses the safe configured acknowledgment.

Remaining edge: a process crash after assignment but before V4 acknowledgment
can leave the customer without that acknowledgment, even though assignment is
durable. This failure window needs an explicit recovery acceptance test before
LIVE. Do not confuse paused/queued/assigned states in operational review.

13. DEFERRAL FLOW

Latest evidenced readiness updates the small state. DEFERRED/DECLINED blocks
invoice creation and payment/proceed pressure. Existing purchase facts remain
available for legitimate questions. A later explicit READY_TO_PAY plus current
payment request can resume. No customer phrase matching is used in backend.

14. COURSE DETOUR FLOW

ASK_COURSE_DETAILS with KEEP answers course questions without erasing ads work.
An explicit REPLACE with COURSE changes the purchase. Returning to advertising
uses actual history/new interpretation and preserves no guessed V1/V2/V3 state.
It does not restore an archived management object automatically; facts must be
re-established from actual available context when needed.

15. MULTI-QUESTION / RAPID-MESSAGE FLOW

Existing debounce/batching supplies one current inbound batch to interpreter.
Each current request carries evidence. Resolver collects independent facts and
knowledge; unsupported questions are listed separately instead of discarding
supported ones. Composer must declare coverage for every request, including
explaining an unavailable answer. Semantic completeness still needs human review.

16. OLD-CONVERSATION MIGRATION

First V4 processing creates only ai.v4 state. It seeds bounded actual inbound
and successfully sent/delivered/read outbound messages, not unsent drafts.
Trusted invoice/payment/ownership data is loaded separately. V1/V2/V3 inferred
states and V3 remote conversation IDs are not conversational truth for V4.
Engine switches preserve data. Returning V4 sees intervening actual history;
longer gaps outside the history bound remain a real-model acceptance concern.

18. TEST AGENT

Select V4 in the existing Test Agent. Sessions are server-owned, actor-scoped,
expire after one hour, and preserve multi-turn simulated delivered history.
Client-submitted state/IDs cannot attach tests to real customer conversations.
Reset conversation clears the selected test session. A simulated handoff stops
further AI turns until reset. Restarting backend expires in-memory test sessions.

State and decision exposes interpreter output, merged state, selected backend
operations, knowledge, quote, simulated actions, Answer Pack, composer attempts,
validation errors and per-pass model/tokens/cache/cost/latency. Input and final
response are displayed in the transcript. Test logs/usage accounting can be
stored; customer messages/invoices/assignments/payments are never test effects.
Clicking Test Agent later WILL use paid OpenAI calls unless a mock is supplied
by tests. No such paid request was made in this implementation task.

19. MODEL / COST / CACHE SETTINGS

Interpreter: gpt-6.1-sol, medium. Composer: gpt-6-luna, medium.
Settings -> V4 Simplified configures each independently. Composer may be set
to gpt-6.1-sol for later acceptance testing. Unknown model availability is not
proved by a syntactically valid model name. API errors remain observable.

Default history: 40 actual messages; configurable 4-80.
Default output limit: 4,000 tokens per pass; configurable 1,000-12,000.
Existing maxResponseLength applies to final text (default 1,500 characters).
Input batch bounded at 200 messages/40,000 serialized characters; history over
60,000 serialized characters fails safely rather than silently sending a dump.
Responses API store:false; no persistent remote V4 conversation or tool loop.
Stable instructions/schema precede changing payload to support provider caching.
Caching is measured when returned, not assumed or guaranteed.

Current standard estimate per million tokens (USD):
gpt-6.1-sol: input 2.00; cached input 0.10; output 10.00; cache write 2.50.
gpt-6-luna: input 0.10; cached input 0.01; output 0.50; cache write 0.125.
Unknown/custom model cost is null rather than guessed. Provider failures count
as attempted passes with unknown cost when usage is unavailable.
This task's paid-model calls: zero. Paid-model cost: $0.
