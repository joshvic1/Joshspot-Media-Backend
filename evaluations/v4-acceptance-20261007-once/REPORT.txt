3. INTERPRETER FAILURES

B4 and E4: interpreter supplied readiness INTERESTED with evidence:null.
Backend requires current-message evidence for non-UNKNOWN readiness. The JSON
schema accepts this combination, but the semantic contract rejects it.
C3: breakdown and inclusions were extracted, but both got the same request ID.
The duplicate-ID guard rejected it before composition. C3 also had the same
null readiness-evidence problem, hidden behind the first rejection.

This is a contract failure, not evidence that the model misunderstood all
customer meaning. Setup/management selection, daily budget, package selection
and the mixed pair were interpreted correctly in the reached examples.
No JSON parse/Responses API schema/provider failure occurred.

8. FINAL VALIDATION FAILURES

Three distinct financial false-positive mechanisms were observed:

a. Numeric suffix parsing: D1 reads the m in '30000 management fee' as million,
   resulting in30000000000. G1 similarly consumes the m in ', making' after
  25000, resulting in25000000000. Those are parser artifacts, not model prices.
b. Role attachment: G1 repair correctly says60000 total,35000 advertising,
  25000 management; nearest-word logic assigns35000 to total and25000 to
   advertising_budget. Correct prose is rejected.
c. Previous customer budget provenance: B3 first reply repeats5000 daily.
   That fact exists in quote inputs/history but current customerFacts only
   contains duration; approved financial facts lack the daily figure. Repair
   removed it. Relevant confirmed numbers cannot reliably be repeated.

H2 FALSE_PAID_CLAIM is also a false positive: 'I can’t confirm your transfer yet;
payment hasn’t been verified on our end.' Curly-apostrophe negations are not
recognized by the narrow negation expression. The model did NOT claim payment
was confirmed. REQUEST_COVERAGE also correctly rejected its extra old price ID.

The one permitted repair did not fix D/F/G/H. No validators were changed.
diagnostic-review.txt records offline inspection of already-saved parser output;
this inspection made no model call and did not rerun a scenario.
